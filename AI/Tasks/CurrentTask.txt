TechToolbox v2.2 Runtime Data Root Migration
=============================================

Goal
----
Perform a complete, safe, governed migration of all TechToolbox runtime data
from the installed module directory (ModuleRoot) into the machine-local,
non-roaming runtime root:

    $env:LOCALAPPDATA\TechToolbox\

This migration includes analysis, diff generation, and code implementation.
All phases are authorized within this single task, but must follow the
governed multi-phase workflow defined below.

Multi‑Phase Workflow (Unified)
------------------------------

Phase A: Analysis
    - Analyze the current TechToolbox path architecture.
    - Identify all affected files, consumers, and path dependencies.
    - Produce the proposed path dependency graph.
    - Identify all required changes.
    - No code mutation is allowed in Phase A.

Phase B: Diff Generation
    - Produce literal, line-accurate diffs for every file identified in Phase A.
    - Diffs must be complete patch blocks that can be applied directly.
    - Diffs must correspond exactly to the Phase A plan.
    - No code mutation is allowed in Phase B.
    - If any diff cannot be produced without guessing, request clarification.

Phase C: Implementation
    - Apply only the diffs produced in Phase B.
    - Modify only the files listed in Phase A.
    - No additional changes may be invented.
    - All mutations must follow the v2.2 migration contract.
    - All mutations must integrate with the existing $script:TT architecture.
    - All mutations must preserve packaged assets under ModuleRoot.
    - All mutations must ensure LocalDataRoot is authoritative for runtime state.
    - All mutations must preserve call-site export overrides.
    - All mutations must be idempotent.
    - After mutation, produce a full diff summary of all modified files.

Phase D: Validation
    - Validate all acceptance criteria.
    - Confirm no runtime writes occur under ModuleRoot.
    - Confirm all runtime paths resolve exclusively through LocalDataRoot.
    - Confirm packaged assets remain untouched.
    - Confirm Test-TTPathRoots reports correct invariants.
    - Confirm initialization is idempotent.
    - Confirm Update-Module does not require runtime-state migration.

Phase E: Regression Testing
    - Run all path-resolution tests.
    - Run all logging/export tests.
    - Run all secrets initialization tests.
    - Run all AI/AgentRuntime path-consumption tests.
    - Run all cross-version coexistence tests.
    - Report any remaining ModuleRoot writes.

Architectural Contract
----------------------
ModuleRoot = immutable application assets.
LocalDataRoot = mutable runtime/user state.

No normal runtime operation may write to ModuleRoot.

Packaged assets remain under ModuleRoot:
    AgentRuntime\
    AI\
    artifacts\
    Config\
    en-US\
    Formats\
    Private\
    Public\
    Workers\

Live runtime state must reside under:
    $env:LOCALAPPDATA\TechToolbox\

This includes:
    Config\config.secrets.json
    Logs\
    Exports\
    any future runtime state

Secrets Initialization Contract
-------------------------------
During module import:
    - Ensure LocalDataRoot and its subdirectories exist.
    - If LocalDataRoot\Config\config.secrets.json exists:
          leave it untouched.
    - If it does not exist:
          initialize it from ModuleRoot\Config\config.secrets.json.
    - Never overwrite an existing LocalDataRoot secrets file.
    - Never search older module versions for secrets.

Path Authority
--------------
There are exactly two authoritative roots:
    ModuleRoot
    LocalDataRoot

All other paths must derive from these.

No path may derive from:
    Documents
    OneDrive
    PSModulePath
    older module versions

Acceptance Criteria
-------------------
Migration is successful only when:
    - ModuleRoot is immutable.
    - LocalDataRoot is authoritative.
    - No runtime writes occur under ModuleRoot.
    - Packaged assets remain intact.
    - Secrets survive Update-Module.
    - Logs survive Update-Module.
    - Exports survive Update-Module.
    - Call-site overrides remain authoritative.
    - Test-TTPathRoots reports correct invariants.
    - Initialization is idempotent.
    - No legacy config is discovered.
    - No cross-version path bleed occurs.
    - No cloud-synced location is chosen implicitly.

Authorization
-------------
This unified task explicitly authorizes:
    - Phase A analysis
    - Phase B diff generation
    - Phase C code mutation
    - Phase D validation
    - Phase E regression testing

Code mutation is authorized ONLY in Phase C and ONLY using the exact diffs
generated in Phase B.

The model proposes. The orchestrator decides.
