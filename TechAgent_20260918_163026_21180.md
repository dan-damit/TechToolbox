## Analysis: techtoolbox-local allowedTools are not visible

### What the configuration contains

`Config/config.json` defines `techtoolbox-local` as enabled and allowlists exactly these four functions:

- `Get-AllUsers`
- `Get-SystemUptime`
- `Get-SystemSnapshot`
- `Get-TechToolboxConfig`

`TechToolbox.psd1` exports all four functions. Therefore, the configured names match the module's exported function names exactly, including capitalization-insensitive matching.

### What the adapter does

`TechToolbox.LocalMcpAdapter/Program.cs` reads the allowlist only from the process environment variable:

`TT_AGENT_MCP_CONFIG_JSON`

It then:

1. Parses the JSON root.
2. Looks for a top-level `servers` array.
3. Finds a server whose `name` equals the requested `--server-name`.
4. Reads that server's `allowedTools` array.
5. Discovers PowerShell functions with:
   `Get-Command -Module 'TechToolbox' -CommandType Function`
6. Keeps a discovered command only when it is in the allowlist.

The filtering condition is explicit:

`if (_options.AllowlistedCommands.Count > 0 && !_options.AllowlistedCommands.Contains(name)) continue;`

### Most likely reason the four tools are not visible

The adapter does not read `Config/config.json` directly. It has no config-file loading logic. It depends entirely on `TT_AGENT_MCP_CONFIG_JSON` being present in the adapter process.

The normal `Invoke-TechAgent` path is intended to provide that variable. `Invoke-TechAgent.ps1` clones the configured MCP server objects, serializes them into `serializedMcpConfigForChild`, places that value in the agent request as `McpConfigJson`, and the child script sets:

`TT_AGENT_MCP_CONFIG_JSON`

before loading the agent assembly. The MCP child processes inherit that environment.

Consequently, if the adapter is launched directly, launched outside the normal `Invoke-TechAgent` child process, or launched by an older/stale runtime path, the variable is absent. `ResolveAllowlistFromMcpConfig` then returns an empty set. The adapter will expose all discovered module functions rather than the four configured functions, or expose none if module discovery fails. The configuration file itself is not sufficient to configure a standalone adapter process.

### Important distinction

The allowlist is an adapter-side discovery filter. The agent-side MCP client separately calls `tools/list` and registers whatever the adapter returns. The adapter does not send the four configured names as tools merely because they exist in `config.json`; they must first be discovered from the imported PowerShell module.

### Secondary failure points to verify

- The running adapter binary may be stale. The configuration launches `src\\TechToolbox.Agent\\TechToolbox.LocalMcpAdapter\\bin\\Release\\net8.0\\TechToolbox.LocalMcpAdapter.dll`; source changes do not affect that DLL until it is rebuilt.
- `TT_AGENT_MCP_CONFIG_JSON` must contain a top-level `servers` array and a server named exactly `techtoolbox-local`. The adapter silently returns an empty allowlist for missing, malformed, or differently shaped JSON.
- The adapter must import the intended `TechToolbox` module. It resolves a manifest through `--module-manifest`, `TT_ModuleRoot`, or ancestors of the current directory. If none resolves, it falls back to the module name `TechToolbox`, which depends on PowerShell module discovery paths.
- Discovery requires PowerShell to return the functions under module name `TechToolbox`. If import fails or returns no functions, the adapter cannot expose the allowlisted entries.
- The current repository evidence shows no adapter-side diagnostic output for the resolved server name, environment-variable presence, resolved allowlist, module path, or discovered command names. A silent empty allowlist or discovery failure is therefore difficult to distinguish from successful filtering.

## Conclusion

The four configuration entries and the module exports are consistent. The strongest implementation-level explanation is that the running adapter process is not receiving the serialized MCP configuration, or that the running DLL is not the current implementation. The adapter reads no config file itself and silently treats a missing or malformed `TT_AGENT_MCP_CONFIG_JSON` as an empty allowlist.

The next diagnostic should be to inspect the actual adapter process environment and issue a direct `tools/list` request against the exact configured DLL. That will distinguish configuration propagation, stale binary, module import/discovery, and agent-side registration problems.
